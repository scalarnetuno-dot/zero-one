Chapter 17 delivered an API that keeps products in memory. Before swapping
the memory for a database, you have to decide **what** to store. That
decision is the most lasting one in the project: technologies change,
models stay.

## Entity: the noun that has an identity

A product is not a value — it is a thing. Two products with the same name
and the same price are different products, because they are different items
in the stock. That has a name: `Product` is an **entity**, and an entity
has an **identity**.

:::key
The test is this: *if every attribute is the same, are they still
different things?* If so, it is an entity and needs an id. If not — like an
address, a color, an amount of money — it is a **value**, and a `record`
from chapter 12 does the job.
:::

## The attributes, one by one

```java title="Product.java — the draft" numbered
public class Product {
    private Long id;
    private String name;
    private String description;
    private BigDecimal price;
    private Integer quantity;
    private Status status;
    private Instant createdAt;
}
```

Each type there is a decision, and every one is worth defending.

| Field | Type | Why |
|---|---|---|
| `id` | `Long` | holds 9 quintillion; `Integer` overflows at 2.1 billion |
| `name` | `String` | with a size limit in the database |
| `price` | `BigDecimal` | money is not `double` (chapter 3) |
| `quantity` | `Integer` | an object, not `int`: allows null while undefined |
| `status` | `Status` | an enum, not text (chapter 12) |
| `createdAt` | `Instant` | an absolute moment, no time zone |

Table: Types chosen for a reason, not out of habit.

:::pitfall
`Long` and `long`, `Integer` and `int` are not the same thing. The first
ones are objects and accept `null`; the second ones are primitives and start
at zero. In a database entity, always use the objects: a `long id` is
already `0` before saving, and `0` is indistinguishable from "doesn't have
an id yet".
:::

## The primary key

Three strategies, and you will find all three in real code:

| Strategy | Example | When |
|---|---|---|
| Sequential | `1, 2, 3` | default; simple and readable |
| UUID | `9f1c...` | distributed data, id generated by the client |
| Natural | `ssn`, `sku` | almost never: business data changes |

Table: A sequential key solves most cases. It is the book's choice.

:::pitfall
Using a piece of business data as the primary key looks elegant and sends
the bill later. The supplier's SKU changes; the tax ID is typed wrong; the
customer's e-mail gets updated. When that happens, you find out the key is
copied into six tables. A primary key should be a number with no meaning —
it is the only thing that never needs to change.
:::

## Relationships: who knows whom

```text title="The sentence that defines the relationship"
A category has many products.
A product belongs to one category.
```

Those two sentences describe the same relationship seen from both sides —
and that is the essence of chapter 29. In a database, it materializes as a
**foreign key** in the table on the "many" side:

:::diagram type="blocks" caption="The foreign key lives on the side that has many."
flow: false
rows:
  - [{ text: "category", note: "id · name" }]
  - [{ text: "product", note: "id · name · category_id →" }]
:::

| Cardinality | Example | Where the FK goes |
|---|---|---|
| 1:N | category → products | on the product |
| N:1 | product → category | on the product (same thing) |
| N:N | product ↔ tag | in a join table |
| 1:1 | user → profile | on either of the two |

Table: The four cardinalities. Most real relationships are 1:N.

The modeling meeting lasted two hours and produced a drawing on the

At the ninety-minute mark, Cláudia remembered something.

"Oh, and there are the services."

"Services?"

"Installation, setup, extended warranty. We sell those too."

"And is that a product?"

"It is and it isn't. It has no stock. But it has a price. And it shows up

Marina turned the marker in her hand for a few seconds.

"How many services are there today?"

"Three."

"And how many products?"

"Eleven thousand."

She drew a box in the corner of the board, wrote `Product` inside and a
`type` field below it. Then she drew a class hierarchy next to it, with
`Product` as the parent, and crossed it out.

rules, we split them. Modeling a future that may never come costs more than
changing later."

## Three questions that prevent refactoring

Before writing the first line of SQL, answer:

1. **What identifies this?** If the answer is "the name", think twice —
   names repeat.
2. **Can this field be null?** Every optional field is one more `if` in the
   code, forever.
3. **Is this data historical or current?** The current price is one field.
   The price on the date of the order is another field, on the order.
   Confusing the two is the classic defect of any sales system.

:::trivia
Question 3 has a name in real systems: *snapshot*. When a customer buys for
R$ 100 and the price goes up to R$ 120, the old order has to keep showing
R$ 100. Big stores copy the price, the name and even the description into
the order item — an intentional duplication, because the order is a
historical document and not a mirror of the catalog.
:::

## Package structure

From here on the project has packages by **feature**, not by technical
type:

:::tree title="Package by domain, not by layer"
com/store/catalog/
  CatalogApplication.java
  product/
    Product.java              # entity
    ProductRepository.java    # data access
    ProductService.java       # rules
    ProductController.java    # HTTP
    dto/
      ProductRequest.java
      ProductResponse.java
  category/
    Category.java
  shared/
    exception/
:::

:::compare left="By layer (avoid)" right="By domain (prefer)"
controller/
  ProductController
  OrderController
service/
  ProductService
  OrderService
---
product/
  ProductController
  ProductService
order/
  OrderController
  OrderService
:::

The difference shows up when the system grows. In the by-layer
organization, touching products means opening four distant folders; in the
by-domain one, everything about products is in one place. And deleting a
feature becomes deleting a folder.

:::summary
- An entity has an identity and needs an id; a value does not.
- `BigDecimal` for money, `Instant` for a moment, an enum for a closed
  set, `Long` (not `long`) for an id.
- A primary key is a number with no business meaning.
- A 1:N relationship puts the foreign key on the "many" side.
- Organize packages by domain, not by layer.
:::

:::checkpoint
You tell an entity from a value, choose types and keys with a
justification, identify the cardinality of a relationship and organize
packages by domain.
:::

:::exercise level=1
List the fields of `Customer` with their types and justification. Include
a field that can be null and explain why.

:::answer
`id: Long`, `name: String`, `email: String` (unique), `phone: String` (can
be null: not every customer provides one), `createdAt: Instant`. Every null
field is a decision: a null `phone` means "not provided", and the code that
sends text messages will need to handle it — forever.
:::

:::exercise level=2
Model a shopping cart. Decide whether `CartItem` is an entity or a value
and justify it.

:::answer
It is an entity, with a caveat. Two items of the same product in the same
cart could be merged (adding up the quantity), which suggests a value. But
if the system needs to know *when* each item was added, or to allow
different prices per item (a promotion applied to only one), each item gets
its own identity. The answer depends on the requirement — and that is why
modeling is a conversation, not a technique.
:::

:::exercise level=3
A product's price changes. Draw how your model preserves the historical
value of orders already placed.

:::answer
`OrderItem` keeps a `unitPrice` copied at the moment of purchase, besides
the `product_id`. The foreign key is for tracing which product was sold;
the copied price is for the historical document. Without that duplication,
a price adjustment would rewrite the past of the whole database — and it is
one of the most expensive bugs a sales system can have.
:::
